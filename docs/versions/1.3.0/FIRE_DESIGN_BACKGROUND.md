# 双 ChatGPT 账号隔离与点火：设计背景

本文是 1.3.0 双账号与点火功能的原始设计依据。底层素材来自用户于 2026-09-16 提供的本机实施记录；迁移时做了脱敏与收窄，仅保留仍然有效的设计结论。

## 来源与处理说明

- 原始文件位于仓库根目录，未纳入 Git，包含本机机器名、用户主目录绝对路径、`launchctl` 输出、点火 token 用量和外部脚本的操作步骤。
- 本文只保留设计判断，不含机器名、绝对路径、token 用量、进程号或逐步操作说明；其余内容随原始文件一并删除。
- 上文涉及的路径一律写成 `~/.codex-minget-a`、`~/.codex-minget-b` 这种相对当前用户主目录的形式；实现不得改写为个人绝对路径。
- 1.3.0 已实现本文大部分内容，因此本文按「设计背景」而非「待办」阅读；仍未实现的部分集中在文末列出。

## 1. 背景：为什么要「点火」

用户的 ChatGPT 5 小时额度窗口只有在发出一次真实请求后才会开始计时。希望在需要窗口覆盖的时间段开始时，主动发出一次极轻量请求来「点火」，让该账号的新 5 小时窗口尽早开始。

目标（当时的原始表述）：

1. 同时显示两个 ChatGPT 账号各自的额度信息。
2. 两个账号认证完全隔离，避免串号。
3. 两个账号能够分别手动点火。
4. 两个账号能够同时点火。
5. macOS 能够按固定时间自动给两个账号点火。
6. 后续把点火状态、最近执行时间、成功／失败状态整合进 Minget 界面。
7. 保持方案稳定、简单，并避免修改既有 Codex Desktop 与 OpenClaw 的认证配置。

## 2. 双账号隔离设计（已确认的结论）

- 不复用默认 `~/.codex`，也不复制既有 `auth.json`。
- 为两个账号分别建立独立的 `CODEX_HOME`：账号 A 使用 `~/.codex-minget-a`，账号 B 使用 `~/.codex-minget-b`。
- 两个账号各自完成独立 OAuth 登录，认证文件互不复制、互不引用。
- **安全边界：不读取、输出、上传或提交 `auth.json` 内容。** Minget 自身不打开、不列出、不解析、不复制这两个目录中的任何文件；只把目录路径作为环境变量传给官方 Codex CLI 子进程。
- 业务逻辑不得写死「账号 A／B」，应使用可扩展的 Account Profile：ID、显示名、短标签、相对 `CODEX_HOME` 路径分开放置，便于后续增加第三个账号而不改核心架构。

Minget 侧的实际落地：两个固定只读 Profile（`chatgpt-a` / `chatgpt-b`），每个 Profile 一个长生命周期 `codex app-server` 子进程，独立失败预算与独立缓存命名空间。

## 3. 点火模型与固定参数

- 初次验证认证链路时未指定模型，CLI 使用了当时的默认模型与 `reasoning effort = none`。
- 正式点火改用低推理模型，并固定 `reasoning effort = none`，让点火请求的推理开销降到最低。
- 两个账号可以并行点火，窗口开始时间能够控制在非常接近的时刻。

固定调用参数（Minget 1.3.0 与外部脚本共用同一组形态）：

```text
exec --ephemeral --sandbox read-only --skip-git-repo-check \
     -C <临时工作目录> -m <点火模型> -c model_reasoning_effort="none" \
     "Reply exactly: OK"
```

参数用意：

- `--ephemeral`：不保留不必要的会话。
- `--sandbox read-only`：不给点火任务写文件权限。
- `--skip-git-repo-check`：不要求工作目录是 Git 仓库。
- `reasoning effort = none`：最低推理需求。
- 低推理模型：降低单次点火的成本。

Minget 1.3.0 的实际落地：应用内手动点火由 `Process.executableURL` 直启官方 `codex`，不经过 shell、不调用外部脚本；子进程 `stdout`／`stderr` 持续 drain 后丢弃，不写入日志、UserDefaults 或文档；超时 120 秒，terminate 后等待 3 秒，仍未退出时只对本次 PID 发送 `SIGKILL` 并回收。

## 4. 外部脚本与 launchd 定时

用户侧的自动点火基础设施（Minget 不创建、不修改、不调用）：

- 外部脚本 `~/.local/bin/minget-fire`，支持 `a`、`b`、`all` 三个子命令。
- 日志目录 `~/Library/Logs/Minget/`，按账号分开记录。
- LaunchAgent `~/Library/LaunchAgents/com.minget.chatgpt-fire.plist`，三个每日触发时刻。

### 4.1 触发时刻的间隔设计

设计上给上一个约 5 小时窗口预留约 5 分钟安全间隔，避免服务端实际记录的窗口开始时间比本地触发时间晚几秒、导致下一次请求仍落入旧窗口。据此得到三个大致连续的工作日窗口。

### 4.2 已知边界

- LaunchAgent 是用户级任务：Mac 关机、重启后停留在登录界面、或触发时刻无法执行用户任务时，都不能保证点火准时发生。
- **合盖／深度睡眠时，单靠 `launchd` 不应视为可靠的精确唤醒方案。** 若要求严格准点点火，需要另行研究电源管理与自动唤醒，属于未实施能力。
- 自动点火的状态应以实际 `launchd` 状态与执行日志为准，不能只看界面开关。

Minget 侧边界：1.3.0 与 1.3.1 都不生成、编辑、bootstrap、bootout、删除或调用该 plist 与脚本，也不把外部点火日志作为产品状态来源。

## 5. 安全与数据边界（约束后续实现）

1. 不破坏既有双账号认证，不把两个账号重新合并到默认 `~/.codex`。
2. 保留 `~/.codex-minget-a`、`~/.codex-minget-b`。
3. 不读取、打印、上传、提交 OAuth token 或 `auth.json`。
4. 点火失败时记录固定分类原因，但不自动删除或覆盖认证。
5. 额度查询与点火解耦：Usage Provider 负责读取额度，Account Profile 负责账号身份与 `CODEX_HOME` 映射，Fire Service 负责点火，Scheduler 负责 `launchd`，界面只负责展示与操作。
6. 诊断只记录 Profile ID、固定结果分类和自有子进程生命周期。

## 6. 已落地与未落地

已由 1.3.0 落地：

- 双 ChatGPT 账号额度读取与两张独立卡片。
- 可选择的菜单栏来源（账号 A／账号 B／DeepSeek）。
- 应用内手动点火（每个账号一个按钮），以及「请求成功」与「新窗口已确认」的区分；1.3.1 进一步细化为三态。

仍未实施：

- 自动点火开关、定时表编辑与 `Fire All`。
- 点火历史与点火状态面板（当前只保留每个账号最近一次结果）。
- 睡眠状态下的可靠定时唤醒。
- 第三个及更多账号的配置界面（底层 Profile 模型已按可扩展设计）。
